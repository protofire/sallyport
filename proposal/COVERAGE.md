Companion to the proposal (filed as a GitHub issue in logos-co/rfp) and `proposal/MILESTONES.md` (acceptance criteria). Every row that is not Done names the milestone that closes it.

- **Part A** — RFP-021 (Trustless Ethereum State Attestation for LEZ): every requirement, hard and soft (64 rows).
- **Part B** — RFP-022 (Privacy-Preserving Wrapped ERC-20 and Ether Bridge for LEZ): requirement map, what is not met at final acceptance, trust model, correlations left observable, design-rationale answers, questions for Logos.
- **Part C** — Long-form material referenced from the proposal: the full disclosures, the reuse assessment (RFP-021 R6), the release-candidate run latency breakdown, the known-gap lists of both parts, and the full RFP-021 prototype detail.
- **Part D** — Sources for every number in the proposal.

Paths are relative to the repository root.

## Part A — RFP-021 coverage matrix

Status key: **Done** = implemented and evidenced in this repo (test, live transcript or measurement named in the row);
**Partial** = some of it exists, the gap is named; **Not yet** = nothing in the repo; **Milestone** = by definition a
later milestone (audit, catalog release).

**Counts (64 rows): 28 Done, 28 Partial, 5 Not yet, 3 Milestone.** Counted from the Status column of the tables below
(live evidence: final run at development commit `c380d4b`, with the 2026-11-05 `82bb54d` run where labelled). F5, U3, R9, later F6, then F12, and P5 (its breakdown comes only from the superseded release-candidate run) moved from Done to Partial after external review; the gap
is named in each row. The dependency row at the end (LP-0012 events) is not an RFP requirement row and is not counted. Decision IDs (`D-…`) refer to entries in docs/DECISIONS.md.

  deployed there (S1).

#### Not met at final acceptance

Even after B1–B5 (and O, if exercised), these RFP-022 requirements are **not met**, and no milestone claims them:

**Loss bound for compromised root signers, per token** (`docs/ARCHITECTURE.md` §3.1, §3.7). Forged root accepted at `t_a`, release delay `D`, release cap `C` per fixed window `W`, freezer's `freeze` or `revokeRoot` at `t_a + T`:
- `T ≤ D`: loss 0.
- `T > D`: loss ≤ `min(escrow, C · (1 + ⌈(T − D)/W⌉))`. The `+1` is the full cap that can leave in the first block after `D`.
- Freezer never acts, or its key is compromised too: loss = the whole escrow, for every token.

Demo values: `D = 600 s`, `C = 2·d`, `W = 24 h`, escrow ≤ `4·d` per token.

### B.4 Answers to the design-rationale questions

- **Denominations (F8).** Fixed per-token denominations on both chains; the anonymity set is per (token, denom). Committed amounts (Soft 1) are not offered; X2 documents a migration path that keeps the vault and the accumulated anonymity.
- **Finality (F12), provisional defaults.** *Ethereum → LEZ:* mint only against a block covered by an RFP-021 header recorded after Ethereum finality (Casper FFG finalized checkpoint, signed by ≥ 342 of 512 sync-committee members); default extra depth 0 (B1 makes it configurable). Observed wait: 1,065.8 s finality plus attest relay in the final Sepolia run. Residual risk: a finality reversal (needs ≥ 1/3 of stake to be slashed) or 342 colluding committee members (not slashable; the proposal, "Trust assumptions") could mint against a deposit that is not canonical. *LEZ → Ethereum:* `minLezDepth = 10` LEZ blocks, the value deployed on Sepolia (`contracts/bridge/deployments/sepolia.json`, `min_lez_depth`), plus the release delay `D = 600 s`. Residual risk: LEZ exposes no finality signal we can rely on yet (LEZ#1053), so a LEZ reorg deeper than 10 blocks after a root is signed could leave an accepted root whose burn no longer exists, letting the release pay while the wrapped balance survives on LEZ (a Sec6 breach bounded by the release cap); with the interim verifier this depth is enforced by the signers. B4 delivers the final value per direction once LEZ finality is defined. A depth change never invalidates an accepted root or a valid claim.
- **Caps (Sec4), provisional defaults** (as deployed on Sepolia, `sepolia.json` `registration`): per token, deposit cap `4·d` and release cap `2·d` per fixed 24 h window (ETH: `d` = 0.01 ETH, caps 0.04 / 0.02 ETH; USDT: `d` = 100, caps 400 / 200), release delay `D` = 600 s, `MIN_TIMELOCK` 6 h for any loosening, `MAX_DELAY` 7 days. Reasoning: with the loss bound of §B.2, a forged root costs nothing if the freezer acts within `D`, and at most `C · (1 + ⌈(T − D)/W⌉)`, i.e. `2·C` = `4·d` per token, if it acts within one window after `D`; the deposit cap limits how fast escrow at risk can grow. A production deployer scales `C` to the loss it accepts if its freezer reacts within one window, and sets `D` no shorter than the freezer's guaranteed response time. These are demo-sized; B4 gives the final defaults with reasoning.
- **Fees (F13), provisional answers.** *Collection point and LEZ fee:* a LEZ fee at mint (`d − fee`) plus a burn of exactly `d` would leave a single deposit unable to exit, so the prototype fixes LEZ fees at 0 (registration and updates refuse other values) and charges once, at release on Ethereum. *Initial rate and range:* the relayer fee is one published standard value per (token, denom), 1% in the Sepolia deployment (`standard_fee` 1e14 wei of a 0.01 ETH denomination; 1 USDT of 100), bound in the release proof journal; on chain the vault enforces only the immutable cap `MAX_FEE_BPS` = 500 bps (5%), not equality with the standard value, so the standard fee is a client convention and a non-standard fee would fingerprint the release. *Routing:* the fee goes to the relayer address named in the journal (a user can name itself); the recipient receives `d − fee`. *Protocol fee (B1):* a configurable LEZ protocol fee on mint and burn, initial rate 0, a fixed value per (token, denom) set by the admin, denominated in the wrapped token (or an admin-selected native-LEZ option), collected out of `d` at release against a proven fee so one deposit still exits, and routed to a destination the deployer configures.
- **One program pair, one chain pair.** Separation, as the RFP assumes: one configuration and vault per EVM chain, bound by `CONFIG_ID`.
- **Token registry and decimals (F10).** Admin-curated. The LEZ amount is the token's own base unit, so conversion is the identity; registration rejects decimals above 18 or any denomination that does not fit `u128`. Delisting closes deposits and keeps burns open.
- **Migration (Sec8).** New verifier or program = new deployment: the old vault stops deposits, keeps releasing burns of its configuration until drained; new deposits go to the new configuration. Exercised in B4 (and in O for the verifier swap).
- **Failsafe (Sec9), provisional strategy.** On a proven vulnerability: (1) the freezer freezes the affected half per token or globally (shown on Sepolia); (2) it permanently revokes every burn root accepted while the vulnerability was live (shown on Sepolia); (3) any admin loosening is queued behind max(release delay, `MIN_TIMELOCK`, 6 h) and the freezer can cancel it. Recovery then uses only the ordinary user-proven paths, as Sec9 requires: an unclaimed deposit is claimed by its owner on a fixed program version (the claim needs `nk` behind `C`), and an unreleased burn is released by its owner's membership proof against an honest root of a fixed deployment (recipient fixed inside `B`). Nothing lets the admin, the freezer or us name a recipient or move escrow, so it is not a backdoor. What it does not cover, stated as the reason no wider failsafe is built: funds already released through a broken verifier are lost up to the cap bound; moving the old vault's escrow to a fixed deployment needs each user to exit and re-enter, because a vault-to-vault transfer function would itself be a backdoor; and if a root-signer key is lost, burns after the last accepted root stay locked until a signer-set rotation or timelocked escape behind the freezer's veto exists (B4 specifies it or documents why not).
- **Audit.** Left to be procured separately, not in the $59,000 RFP-022 development budget: one engagement with RFP-021. Logos may procure it directly (select, contract and pay the auditor), or Protofire contracts it at cost (the proposal, "Audit").

### C.1 Disclosures (both RFPs)

Plain statements of what the prototypes do not do, or do only with a stated trust or limit. The proposal keeps a short form of each.

1. **LEZ block gas cap and throughput (RFP-021, RFP-022).** On LEZ v0.4 (1806e87), 10M execution gas is the cap for a whole block, not only for one transaction, and 5M is the target the base fee is steered to. A transaction is admitted if the block's charged gas so far plus its declared `gas_limit` is ≤ 10M; the client declares 7.4M + 11.5k·K per `Update` and 1,000,000 per claim. One `Update` uses 6.4–8.9M and raises the base fee by about 4–10%. With an `Update` charged U in the block, 1 + ⌊(9.0M − U)/c⌋ claims of c cycles fit: 19 chained ERC-20 claims (c = 133,717) or 6 inline claims with 30 headers (c = 437,101) beside a final-run finality update (U = 6,583,138), and 4 or 2 at K=170 (U = 8,472,345). A block without an update holds 1 + ⌊9.0M/c⌋ claims: 68 chained ERC-20, 54 native-ETH (c = 169,570) or 21 inline-with-30-headers claims. An `Update` waits for the next block if the block has already been charged more than 2.554M (0.645M at K=170). An update is needed at most about once per Ethereum epoch (6.4 minutes), so most blocks carry none, but every LEZ application shares the same 10M. A BLS precompile is the main lever on this; P8 reports the delta (M2).
2. **Dev-mode LEZ proofs in the live runs (both RFPs).** Every LEZ transaction in the live runs was executed with `RISC0_DEV_MODE=1`: guests ran, no LEZ proof was produced or checked. That removes execution validity, not just a cost: a dev-mode sequencer would accept an unproven private mint. Real proofs were measured separately: RFP-021 proving times on one CPU machine and one GPU box (`docs/BENCHMARKS.md`), one real RFP-021 private-claim proof accepted in a test, one real RFP-022 `Burn` proof in the test harness, and real Groth16 membership proofs verified on Sepolia. Real proofs on a live sequencer are M3 and B2.
3. **The RFP-022 release path is INTERIM and CUSTODIAL.** Burn roots are accepted on Ethereum by 2-of-2 ECDSA signatures from two keys Protofire holds. This is not trustless and does not meet RFP-022's trust model: the two key holders together could drain the escrow, bounded only by the release delay, caps and the freezer. Optional milestone O moves custody to q of N LEZ sequencer committee keys co-signing a finalised checkpoint; it is not trustless either.
4. **Claim window: 448 headers of ancestry (RFP-022).** A deposit can be claimed only if the RFP-021 instance records a finalised header within 448 EL blocks (about 90 minutes) after it, the ancestry bound; headers cannot be backfilled and the vault has no refund. The client refuses to deposit while the instance lags more than 224 blocks (half the window). A relayer outage that starts after the deposit can still strand it in the prototype; a historical-root or refund recovery path is now a B1 criterion (scope addition, B1 price unchanged). (RFP-021 has its own, longer window: an instance with no finality advance for ~29.8 h on Sepolia must be replaced; see "Weak subjectivity".)
5. **Signer-key loss (RFP-022).** The root verifier is immutable and has no rotation. If either signer key is lost, no new root can be accepted: burns already covered by an accepted root still release, every later burn cannot be released, and the remaining escrow stays locked in that vault. What the freezer can do: freeze deposits at once so no new funds enter. Recovery is a new vault and verifier with migration; burns made after the last accepted root have no escape path in the prototype. A signer-set rotation or timelocked escape is part of the B4 failsafe deliverable (Sec9).
6. **`eth_getProof` via raw RPC (RFP-021, used by RFP-022 claims).** Headers and receipts go through `verified_proxy_module`; `eth_getProof` still goes through `eth_rpc_module` unverified, because the verified proxy does not expose it. It moves when Logos' proxy adds the method. Soundness does not depend on it: the program checks every proof against roots from a BLS-verified header.
7. **An RFP-021 instance stopped on Sepolia after a beacon-provider outage (RFP-021, and RFP-022 claims through it).** The long-running instance of the 2026-11-05 run applied its last updates on 2026-11-06 11:41–11:48 UTC. From 11:52 both beacon providers it used (lodestar, publicnode) timed out from our host for about three days. When they answered again (2026-11-09 14:07), the instance's checkpoint was older than Sepolia's ~29.8 h weak-subjectivity window, and every update since was refused with 1105 (690 attempts). The relayers sent nothing invalid, but the instance cannot be recovered: only a new `Init` from a fresh checkpoint and a consumer migration restore service (`evidence/rfp021-final-run.md`, "Shutdown of the 2026-11-05 run"). This is the main documented operational risk. Mitigation in this bid: M1 fault-injection tests for endpoint errors and stalled-instance resume by a new operator, M4 lag detection in the module, and the operator guidance in "Weak subjectivity" above (alert at half the window, at least two independent operators). An end-to-end tested migration to a new instance is priced in M5 (F10 criterion), and stalled-instance resume by a new operator in M1 (R7). **Gap:** alerting on "no applied update for N hours" and a third independent beacon provider are not priced deliverables (alerting is part of our post-delivery operation, below); on mainnet the window is ~15.7 days, on Sepolia a single missed day ends an instance. This is why RFP-021 F12 is Partial.
8. **Admin powers on the Ethereum vault (RFP-022).** The admin can still change a listed token's caps and release delay. Loosening changes (lower delay, higher cap) are queued for at least `MIN_TIMELOCK` (immutable; 6 h on the Sepolia deployment) or the current release delay if longer, and the freezer can cancel them until they mature; tightening applies at once and any release delay is bounded by `MAX_DELAY` (7 days). Shown live on Sepolia: a queued USDT cap loosening cancelled by the freezer (`0x0e6a567f4568f058146b440e311477f2f5656b75c68ddbd07904ff36c3958122`) and both halves frozen in one transaction (`0x0e6297b29af4990d58cb4912afdac0aa52e4f02efc66b97f1d5f2043bfc72913`). This works only if the freezer watches `TokenChangeQueued` (`b22 freezer watch`) and acts within the timelock; a compromised admin plus an inattentive freezer can still loosen limits. On LEZ, `UpdateToken` has no timelock.

### C.2 Reuse assessment (RFP-021 R6)

**Reuse assessment (R6).** Prior work we evaluated: [a16z Helios](https://github.com/a16z/helios) (Rust light client, MIT; release 0.12.0 of 2026-10-05 supports Gloas), [SP1 Helios](https://github.com/succinctlabs/sp1-helios) (Helios inside the SP1 zkVM with a Solidity light-client contract; Zellic audit report in the repository) and [r0vm-helios](https://github.com/boundless-xyz/r0vm-helios) (a fork of SP1 Helios onto RISC Zero, audited by zkSecurity, [report](https://github.com/risc0/rz-security/tree/main/audits/r0vm-helios) dated 2025-04-02; it pins `risc0-zkvm` 2.0 and Helios 0.8.3 of March 2025, last commit 2025-06-09). What we reused: Helios's light-client algorithm (validate/apply, including the rejection of an inconsistent next committee), its generalized-index table and normalised-branch rule, ported into `lc-core` (D-LC-1); `alloy-trie`, `alloy-rlp`, RISC Zero's `blst` fork and keccak coprocessor, `beacon_api_module`, `eth_rpc_module`. Why we verify BLS in the program with our own `lc-core` instead of forking r0vm-helios:
- *LEZ's 10M execution-gas cap (per transaction and per block).* r0vm-helios proves an update off-chain and verifies the proof in a Solidity contract. On LEZ the update guest itself runs under the cap. Helios's `verify_generic_update` hard-wires a full zkcrypto BLS pairing with no seam for a cheaper check; a plain in-guest verify measured 10.45M cycles. Fitting required the residue check and an in-program prepare/verify/apply split.
- *One-transaction update.* That split runs inside one call, so a rotation or finality advance is applied atomically or not at all; the monolithic Helios update function does not allow it.
- *LEZ v0.4 actor model.* The program is a LEZ actor with PDAs and borsh state, not a Solidity contract with serde types; it runs on risc0 3.0.5 against Sepolia on Gloas, while r0vm-helios targets risc0 2.0 and an earlier Helios.
- *Audit surface.* The zkSecurity audit covers r0vm-helios's guest and contract as a whole. After the changes above, little of that audited path would stay unchanged, so its audit would not carry over, and depending on the Helios crate would bring its dependency tree (alloy, eyre, tracing, superstruct, bls12_381) into the guest. The cost of our choice is new code: the light-client port, SSZ merkleisation, header and ancestry decoding, the residue kernel, and the program and consumer integration. That is what the audit must cover.
- *Reliability #6.* The pairing building blocks (RISC Zero's `blst` fork) and the keccak coprocessor are mature and maintained; the residue kernel and the light-client port are not audited, so this row is Partial until the audit and M6 (see "Feasibility, both outcomes" in Part A).

### C.6 RFP-021 prototype detail (full text of the source summary bullets)

The proposal's Project Summary and Technical Approach keep the headline figures; the full statements, including the block-admission arithmetic and the earlier live runs, are:

- **Every light-client update, committee rotation included, is one transaction: 6.4–7.0M cycles typical; worst case K=170 non-signers is 8.5–8.9M; all under LEZ's 10M execution-gas cap, which is also the per-block cap (see Block share).** Executor at development commit `82bb54d`: finality 6,559,273, committee-learning 6,981,423. The client sends one `Update` for every update kind up to K=170 non-signers (the 2/3 participation limit); at K=170 the executor measures 8,472,345 (Sepolia), 8,471,460 (mainnet) and 8,866,373 (committee-learning), under the 9.5M budget the client keeps. These are measured at sampled K including 170, plus a boundary search, not at every K; cost grows monotonically with K. Live: rotation 6.41M, finality 6.55–6.61M, committee-learning 6.97–7.03M. A plain in-guest BLS verify measured 10.45M cycles, over the cap. What makes a whole update fit is the residue kernel: the final exponentiation is replaced by a check of a prover-supplied residue witness (Novakovic–Eagen, ePrint 2024/640), so the update runs the shared two-pair Miller loop plus that check. The earlier two-transaction split (`UpdateBegin`/`UpdateVerify`) remains only as a fallback above K=170; at today's 342-signer floor K cannot exceed 170, so the fallback is unreachable now, and we keep it only because the program is immutable and a future committee size or fork that raises per-update cost would otherwise need a new program version.
- **Block share.** In LEZ 1806e87, 10M is the per-block execution-gas cap and 5M the target the base fee is steered to (`fee/core/src/market.rs:10-15`, `chain_state/src/apply.rs:635`); the sequencer admits a transaction only if the block's used gas plus the transaction's declared `gas_limit` fits under 10M (`sequencer/core/src/lib.rs:144`). One `Update` therefore uses 64–89% of a block and is over the 5M target on its own: each update block raises the base fee (controller damping 8: about +4% at 6.6M, +9.8% at 8.9M). Admission uses declared gas against what the block has already been charged: a transaction enters if the gas actually charged to the transactions already in the block plus its own declared `gas_limit` is ≤ 10M (`DeclaredGasBudget::fits`, re-synced to charged gas after each transaction, `sequencer/core/src/lib.rs:144,2210`). The client declares 7.4M + 11.5k·K per `Update` (7,446,000 at K=4 in the final run; 9,355,000 at K=170) and 1,000,000 per claim. So: (a) an `Update` enters a block only while that block has been charged ≤ 10M − 7.446M = 2.554M (≤ 0.645M at K=170), otherwise it waits one block; (b) behind an `Update` charged U, the last claim enters while the block is charged ≤ 9.0M, so the block takes 1 + ⌊(9.0M − U)/c⌋ claims of c cycles: at U = 6,583,138 (final-run finality) that is 1 + ⌊2,416,862/133,717⌋ = 19 chained ERC-20 claims or 1 + ⌊2,416,862/437,101⌋ = 6 inline claims with 30 ancestry headers; at K=170 (U = 8,472,345) it is 1 + ⌊527,655/133,717⌋ = 4 or 1 + ⌊527,655/437,101⌋ = 2.
- **Final live run (development commit `c380d4b`, 2026-11-10, reproducible Docker-built guests).** From a fresh Sepolia checkpoint, two relayers applied 13 updates (one committee-learning, twelve finality advances), each one transaction; the 13 sends were 13 distinct jobs, none sent by both relayers. The Logos module's `submit_update` then applied one more (Finality(11,545,216), LEZ block 373, try 8). Ten of the 13 relayer updates and the module's are recorded with hash, block and declared gas limit: each declared 7,446,000 (one 7,457,500) instead of the 10M block cap, and one shared block 278 with two private claims; the last three relayer updates (Finality 11,545,120 / 11,545,152 / 11,545,184) are recorded by job and operator only, without hash, cycles or gas limit. Per-tx cycles (9 relayer txs plus the module's): committee-learning 7,004,016, finality 6,581,557–6,592,817. Fresh deposits were claimed through the chained ERC-20 (direct), inline ERC-20 (30 ancestry headers) and native-ETH (2 headers) consumers at 133,717 / 437,101 / 169,570 cycles; a clone vault that claimed a deposit first did not block the real vault; a private claim succeeded, and the same deposit was refused (1250) through a clone private vault; every replay re-executed as 1250. ImageIDs: attest `dbdf349c…fd80`, erc20_receiver `f132dd78…7a25`, eth_receiver `309ad796…4f08`, erc20_inline_receiver `1b62b2f9…8655`; `scripts/image-ids.sh` reproduces them on macOS and Linux (full values under "Public evidence"; `evidence/rfp021-final-run.md` "Final run").
- **Live operation (earlier run, development commit `82bb54d`, non-Docker images).** Two relayers and our Logos module, with no allowlist, advanced one instance from a fresh Sepolia checkpoint: it learned the next sync committee and recorded four finality advances, each update one transaction. The five updates were applied by two distinct operator accounts, all run by Protofire (one relayer's key and the module's fresh key); in that first window the losing operator always saw the state advance and dropped the job before sending. Over the full unattended run (about 19.5 hours), 9 of 183 jobs were sent by both relayers; each duplicate reverted (1106) and nothing was double-applied, but the losing relayer logged its reverted transaction as included (being fixed, see Known gaps). Left running unattended overnight, the relayers carried the instance across the period 1405→1406 boundary: the rotation was one transaction (6.41M cycles), and the stored committee is now the period-1406 one. A beacon-provider outage delayed updates by 19 minutes; the relayers recovered without intervention. Chained ERC-20, inline ERC-20 and native-ETH claims of fresh Sepolia deposits verified through 26–30 parent-hash ancestry headers (391k–578k cycles each). Each replay reverted; re-executing the included replay txs gives 1250 (already claimed) for all three. A fresh Sepolia deposit was claimed privately, and a second claim of it, also through a second vault, was refused (1250). That instance later stopped tracking Sepolia after a beacon-provider outage (Disclosure 7).

**Weak subjectivity (F9, F10).** The period comes from the consensus-specs Electra formula: 279 epochs (~29.8 h) for Sepolia, 3,537 epochs (~15.7 d) for mainnet at current stake. Stale bootstraps and updates are refused (1105). The program cannot read a clock, so `now_slot` is accepted only within ±120 s of LEZ block time. On Sepolia the window is only about 2.5 h longer than one sync-committee period: an instance with no finality advance for ~29.8 h can never be advanced again and must be replaced (this happened to our earlier Sepolia instance; Disclosure 7). Operators must therefore keep updates landing every few hours, alert at half the window, run at least two independent operators, and be ready to `Init` a new instance from a fresh checkpoint and migrate consumers (OPERATOR-GUIDE.md; migration not yet tested end to end; the tested migration is an M5 criterion).

Updates run publicly on the sequencer; no one proves them in this design, and their rows are the cost of a hypothetical private or zk-wrapped update. User-side hardware: provisional minimum 4 cores / 8 GB with `segment_limit_po2 = 18`, recommended 8+ cores / 16 GB (`docs/BENCHMARKS.md` §5). The minimum is extrapolated from a run limited to 4 threads on pre-keccak code (peaks 2.4–3.4 GB) and not measured on such a device; the real private-claim test at default settings on the final code peaked at 8.6 GB (whole test, including a public re-run).
