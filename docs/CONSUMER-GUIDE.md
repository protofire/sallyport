# Consumer guide

For LEZ programs that want to act on a verified fact about finalised Ethereum state. Worked example: `crates/consumers/src/lib.rs` (`erc20_receiver`, `eth_receiver`), run in `crates/program-tests/tests/executor.rs` and live against Sepolia on a local LEZ v0.4.0-rc1 sequencer ([../evidence/rfp021-final-run.md](../evidence/rfp021-final-run.md), dev-mode proofs). The attest program is not deployed on a public testnet (the public LEZ testnet runs v0.3.x). Interface: the message sets in `crates/attest-program/src/lib.rs` and `crates/consumers/src/lib.rs`, published as SPEL-format IDL in `idl/` (hand-shaped, drift-checked; SPEL's client generator is not compatible, see D-MOD-4 in [DECISIONS.md](DECISIONS.md)). Off-chain material: `rfp021 fetch-attest` or the Logos module (`docs/MODULE.md`).

Trust model in one line: the attest program verifies Ethereum finality by sync-committee signatures and a checkpoint fixed at instance creation; off-chain parties are liveness-only. Read `TRUST-ASSUMPTIONS.md` before relying on it.

## Integration flow

1. Choose an instance (`instance_id`, 32 bytes) and verify its checkpoint and every config field yourself (TRUST-ASSUMPTIONS.md section 3). The id is `attest_program::instance_id(cfg, trusted_block_root)`, enforced by `Init`, so pinning the id pins the whole config.
2. A user's `Claim` message to your program carries the EL header RLP, the Merkle proof (account, storage or receipt), the locator and the predicate inputs. Build the request with the same helper the vault uses (`consumers::attest_request`).
3. Your program sends a chained `Attest` message to the header PDA `PDA(attest, header_seed(instance_id, execution_block_hash))`.
4. The attest program verifies the header hash, the proof and the predicates and replies with `AttestReply{instance_id, statement, ctx}` to your program (`attest()` in `program.rs`). Your `on_reply` checks the reply and acts. Everything happens in the claimant's one transaction (F7); no result computed in an earlier tx is consumed.
5. A relayer must have advanced the instance so that a `HeaderRecord` for that block exists; otherwise `Attest` fails with 1101.

### Facts in blocks that are not recorded checkpoints (ancestry)
Only finalised checkpoint blocks get a `HeaderRecord`. To attest a fact in any other finalised block T (e.g. a deposit a few blocks before a checkpoint), pick a recorded block A after it (the anchor) and send `Attest` to A's header PDA with `exec_header_rlp` = A's header and `ancestry` = the header RLPs `[H_T, H_T+1, …, H_A-1]`. The program checks `keccak(H_i) == parentHash(H_i+1)` up to A and verifies the proof against H_T. Empty `ancestry` = the old behaviour.
- Bound: `inclusion::MAX_ANCESTRY` = 448 headers (1001 above it); a broken link is 1201. With the risc0 keccak coprocessor each header costs about 15.6k cycles (log attest at 448 measured 7.11M of the 10M cap; storage slot at 448 estimated 7.27M; D-ATT-7). Prefer the nearest recorded anchor anyway: the request carries ~680 bytes per header (448 headers ≈ 300 KB of tx data). 32 headers cover one epoch: when every epoch's finalised checkpoint is recorded, every finalised block is at most 31 blocks below a recorded one; 448 lets an anchor reach back 14 epochs.
- The fact, and so `statement_id`, names the attested block T (`fact.execution_block_hash` = T, `block_number` = T's), never the anchor: the same event attested via two anchors has one id and one nullifier (test `same_fact_via_two_anchors_has_one_statement_id`).
- The reply then comes from the **anchor's** header PDA, not `header_seed(instance, fact.execution_block_hash)`. A consumer that uses ancestry must check `from == PDA(attest, header_seed(cfg.instance_id, anchor))` with the anchor it sent (keep it in `ctx`, which you set and the program echoes). The reference consumers do exactly this: `Claim` carries `ancestry`, `Claim.block_hash` names the recorded header the request goes to, and `on_reply` checks the sender against `ctx.anchor` (D-CON-2; test `erc20_claim_via_ancestry_and_replay`; live ETH claim via 2 ancestry headers and inline ERC-20 claim via 30 in [evidence/rfp021-final-run.md](../evidence/rfp021-final-run.md)). With empty ancestry the anchor is the fact's own block.
- Relayer: `rfp021 fetch-attest --block-hash <T> --anchor <A> --tx-index i --log-index j` writes the request material (`exec_header_rlp` = A, `ancestry`), linkage checked on the host. Log-only fetches skip `eth_getProof`, so they work on nodes without historical state.

### Compact receipt witness
`Proof::LogCompact { receipt_proof }` (appended tag 3) is `Proof::Log` without the receipt: the receipt is the value of the proven final leaf, which the proof already carries, so the request is about 1 KB smaller and the attest program skips the receipt compare. Same checks and same `Statement` as `Proof::Log` (test `compact_receipt_witness_same_statement`). The reference consumers send it on their chained `Attest`; their `Claim` message still carries `receipt` and is rejected with 1202 unless it equals the proof's final leaf (docs/DECISIONS.md D-GAS-6).

### Optional pattern: inline verification (`erc20_inline_receiver`)
The reference consumers use the single verification path: a chained `Attest` to the header PDA. A consumer may instead verify **inside its own `Claim`** with the same core and only ask the attest program to authenticate the anchor. Example: binary `erc20_inline_receiver` (`consumers::program::handle_inline`, D-GAS-7), test `inline_consumer_claim_binds_header`.
1. Call `attest_program::verify_at(cfg.chain_id, cfg.genesis_validators_root, anchor_hash, &request)`. This is the body of `verify_ref`, the function `Attest` runs (same header/ancestry, proof, predicate and `StatementId` code), evaluated against an anchor that is **not yet authenticated**.
2. In the same transaction, chain `Msg::CheckHeader { instance_id, chain_id, genesis_validators_root, execution_block_hash: anchor_hash }` to `PDA(attest, header_seed(instance_id, anchor_hash))`, **before** any message that moves value. It fails with 1101 unless that header record exists, and with 1204 unless its chain id and genesis validators root equal the ones you verified against. A failure reverts the whole transaction, including your state change and the nullifier.
3. Apply exactly the checks you would apply to an `AttestReply` (the example calls the same `on_reply`).

Measured (executor cycles, `cycle_table`): ERC-20 Claim **120,855** inline vs **155,845** chained on the final code (D-GAS-7 measured 117,043 vs 149,489 before the per-vault nullifier fix).

Trade-offs, why it is not the default:
- Audit surface per consumer. Every inline consumer embeds the verifier and must get the binding right itself (call `verify_at` with its pinned chain/gvr, send `CheckHeader` for the same anchor, keep it in the same tx). With the chained path that logic lives once in the attest program. Forgetting `CheckHeader`, or sending it for a different hash, accepts facts from any header the claimant invents.
- Rejected claims do more work. The proof is verified before the header is authenticated, so a claim against an unrecorded block pays for the full verification before failing 1101, and an input with several faults can report a different first error than the chained path (e.g. 1202 instead of 1101).
- Upgrades. A verifier fix in the attest program reaches chained consumers when they point at the new program; inline consumers must be rebuilt and redeployed themselves.
- `CheckHeader` returns no data and no reply: it is an existence-and-equality check for that one header record.
- Never deploy both patterns against the same vault. The inline (`erc20_inline_receiver`) and chained (`erc20_receiver`) consumers are separate program ids, so their vault and nullifier PDAs live in separate namespaces: a deposit claimed through one is not nullified in the other. Two deployments configured with the same vault address and token would credit one Ethereum deposit twice. Pick one program per (vault address, token).

## Recommended Consumer Pattern

Follow all six rules. The reference consumer implements 1-4 and 6; 5 is a deployment rule.

### 1. Nullifier keyed on the vault and the StatementId (public path only)
The `Statement.id` is `sha256("rfp021/fact/v1" ‖ borsh(chain_id, genesis_validators_root, execution_block_hash, locator))`. It identifies the fact (for a log, a single event), not your predicate. After checking the reply, send a `Nullify` message to `PDA(sha256("rfp021/nullifier/v2" ‖ vault_id ‖ statement_id))` that fails if the account already has state. The reference does this in `on_reply` and `Nullify` (`nullifier_seed`, error 1250 `ERR_ALREADY_CLAIMED`). Test: `erc20_receiver_claim_replay_and_wrong_amount_recipient`; live replays reverted ([evidence/rfp021-final-run.md](../evidence/rfp021-final-run.md)). The nullifier record doubles as the credit record. Because the id excludes the predicate, one event can be consumed once per vault, not once per predicate.

Why the vault is in the nullifier. `InitVault` is permissionless. With a nullifier keyed on `statement_id` alone, anyone could create a clone vault with the identical config, claim each deposit there first, and make the real vault's claim fail 1250 for good (test `clone_vault_cannot_steal_deposit`, which failed before the per-vault nullifier). With `vault_id` in the seed, each vault is its own ledger: a clone can record the same deposit in its own `VaultState`/`Credit`, but cannot touch yours. So **pin your `vault_id`** and count only its state; never add up credits across vaults with the same config. `vault_id` is caller-chosen and not derived from the config, so check a vault's stored config before you pin an announced id.

State facts. For account and storage facts the id contains the block hash, so the same unchanged value at two finalised blocks has two ids (F6 Partial). A nullifier keyed on it stops a replay of one attestation, not a re-claim of an unchanged balance or slot at a later block. Consumers of state facts must add their own uniqueness rule (for example, consume a slot only when it changes, or key on the value and a sequence number held in the slot).

This nullifier is **linkable**: `statement_id` is a public function of Ethereum data, so anyone can map `H(statement_id)` back to the deposit. That is fine for the public path, which reveals the claim anyway. It is wrong for a private claim (F8): there, use a nullifier derived from a secret committed on Ethereum, `N = sha256("rfp021/pnf/v2" ‖ nk)` (global per consumer program, not per vault: a per-vault nullifier lets one deposit be credited once in every vault with a matching config, and here the credit lands in the claimant's own balance, not a vault ledger; front-running needs `nk`, so clones cannot block it) with the deposit carrying `C = sha256("rfp021/commit" ‖ nk)`, and never publish `statement_id` or anything derived only from public Ethereum data ([PRIVACY.md](PRIVACY.md) section 3.3). A LEZ private PDA cannot replace it: private PDAs are per owner, not globally unique.

Private claims (prototype, `PrivateClaim` in `crates/consumers/src/lib.rs`, tests in `crates/program-tests/tests/private.rs`) credit the receiver, so the receiver must be authorized (`ReceiveInput::is_authorized`, the owner's key): otherwise a `PrivateClaim` sent as a public root call writes a balance onto someone else's empty PDA (a nullifier or vault) and blocks it forever (test `private_claim_cannot_squat_public_pdas`). The balance is `PrivateBalance { cfg_hash, amount }`: it belongs to one private-vault config, and a claim through another config is refused (test `private_balance_is_bound_to_vault_config`), so spend logic must check `cfg_hash` against the config it trusts. Every state the reference writes starts with a type tag byte (`consumers::TAG_*`), so one kind cannot be read as another. Private claims do not chain `Attest`, because that publishes the header PDA and so the Ethereum block. They call `attest_program::verify` inside the private transition and prove header membership against the instance's header accumulator; the public part only checks `Msg::CheckRoot` on the root PDA. **Always prove against the latest root**: an older root narrows the deposit to the headers accepted before it.

Never send `PrivateClaim` as a public transaction. As a public root call its message, including `nk`, is in cleartext; anyone who sees the pending tx can copy it onto their own signed account and land first, taking the credit (the depositor's claim then fails 1250). The program does not stop this (a signed public account is authorized; the repo's `private_claim_cycles` test runs it that way to measure cycles). Wallets must only submit it inside a privacy-preserving tx and must not fall back to public execution. Binding the recipient into the commitment (`C = H(nk ‖ recipient)`) would remove it; not done in the prototype.

**`is_authorized` is per account, not per caller, and a balance binds to its first config.** LEZ marks a signed account authorized for every program in the tx, so a hostile program that a user calls in a tx signed with account A can chain `PrivateClaim` into A's empty balance under the attacker's own config (one junk deposit). A's `PrivateBalance` is then bound to that `cfg_hash`, and every later legitimate claim into A fails 1001; there is no reset. Grief only, and it needs the user's signature on a tx that reaches a hostile program. Mitigation for integrators: claim into a fresh account per config; a fix (require `from.is_none()` as the RFP-022 bridge does, or key balances by `cfg_hash`) changes the consumer guest and is not in this build. A root PDA never expires, so a proof made against the latest root stays valid if newer headers land before inclusion.

### 2. Chain binding and instance binding
Store `chain_id` and `genesis_validators_root` in your config and compare both to the fact (`on_reply` -> 1204 on mismatch). Also check **who** replied: the sender must be the header PDA of **your pinned instance** for the header you sent the request to: `from.account_id == PDA(attest, header_seed(cfg.instance_id, anchor))`, where `anchor` is the fact's block when ancestry is empty (see Ancestry above), and `r.instance_id == cfg.instance_id`. This stops a statement from another instance (including a different chain) being accepted (tests `two_instances_do_not_interfere_and_cross_instance_rejected`, and `f5_same_contract_address_on_sepolia_and_mainnet`: same contract address, slot and log locator under a Sepolia and a mainnet instance give different statement ids, and a consumer bound to one chain rejects the other's statement with 1204 or 1101). Recompute `inclusion::statement_id(&fact)` and compare it to `statement.id`.

Re-check your own predicates on the proven fact; do not trust the echoed predicate list (`inclusion::attest(f.clone(), preds(...))` in `on_reply`).

### 3. Handling each typed error code
The program exits with code `N-1000`; LEZ reports `ProgramExitedWithCode{code}` (D-ATT-1). Your transaction reverts; nothing is consumed and you may retry after fixing the cause. LEZ v0.4 blocks carry no revert reason; simulate (executor test API, or the wallet's simulation, which reports e.g. exit 250 = 1250) to read it. A bad aggregate signature or residue witness is the typed 1102 (D-ATT-4), not a trap. Human-readable messages per code: the `errors` table of `idl/attest.idl.json`.

| Code | Name | Meaning / what to do |
|---|---|---|
| 1001 | Malformed | Undecodable input, wrong lengths, wrong PDA, field not applicable. Fix the request; do not retry unchanged. |
| 1002 | ChainMismatch | Fact or update is for another chain id / genesis root. Use the instance for the right chain. |
| 1003 | ForkUnsupported | Fork not in the instance's `ChainConfig`. Create a new instance with an updated config. |
| 1101 | HeaderNotFinalised | No recorded finalised header for that block hash (also: unknown instance, optimistic header). Wait for an operator to advance the instance, or run one; then retry. |
| 1102 | SyncSigInvalid | Signature or hint invalid. Do not retry the same material; fetch it again, and treat repeated failure as an attack signal. |
| 1103 | ParticipationBelowThreshold | Fewer than 342 signers. Wait for a better update. |
| 1104 | HandoffNotVerified | Period gap or `next_sync_committee` proof fails. Submit the missing earlier updates in order. |
| 1105 | CheckpointStale | Outside the weak-subjectivity period. Instance must be replaced (rule 5). |
| 1106 | UpdateNotNewer | Duplicate or already applied. Harmless; stop. |
| 1107 | BootstrapMismatch | Bootstrap does not match the trusted root. Re-verify the checkpoint. |
| 1201 | ExecutionHeaderMismatch | EL header RLP does not hash to the finalised hash, or an `ancestry` header does not hash to the next one's parentHash. Fetch the right headers. |
| 1202 | InclusionInvalid | Proof does not verify under the header's root, or wrong index. Re-fetch the proof. |
| 1203 | PredicateFailed | The fact is real but your predicate does not hold (e.g. wrong amount or recipient). Refuse the action. |
| 1204 | StatementMismatch | Statement does not match fact / chain / instance. Refuse; investigate. |
| 1250 | (consumer-local) | Statement already claimed. Refuse. |

(Numbers 1001-1204 are stable. The codes are exercised by 89 vectors (74 adversarial cases and 15 positive controls), through the host libraries (`cargo test -p vector-runner`, 89/89) and through the on-chain program (`cargo test --release -p program-tests --test guest_vectors`: 84 PASS, 5 UNSUPPORTED, 0 MISMATCH, 0 PANIC; the unsupported ones cannot be expressed in the on-chain message format and are refused by the relayer decoder).)

### 4. Never fall back to unverified input
If the attestation cannot be produced (no header yet, proof window missing, provider down, any code above), **refuse the action**. Do not accept an oracle, a relayer's say-so, a cached value or a manual override as a substitute. The reference vault credits only inside `on_reply`, after every check. The attest program's reply is the only input that moves state.

### 5. Hard-code the attest ProgramId (VS3)
Compile the attest program id into your program as a constant; the reference uses `consumers::ATTEST_PROGRAM` and test `attest_program_id_is_build_constant` keeps the constant tied to the build. **Never** hold the id, or an upgrade pointer to it, in mutable account state, config an admin can set, or a registry. Whoever controls that pointer can substitute a program that attests anything. If you need a new version, deploy a new consumer that has the new constant (migration below). Caveat: the repo's constant is a fixed dev deploy key (`ATTEST_DEPLOY_KEY`); a real deployment must rebuild with the real address.

### 6. Bind the beneficiary to the attested fact
Never trust caller-supplied recipients. A `Claim` can be submitted by anyone who sees the Ethereum deposit, so if the message names who gets credited, a front-runner names themselves. The credit must go to a key fixed by the proven fact. The reference vault has no recipient field: it records the credit against the Ethereum `from` (topic 1) of the attested Transfer log (`Credit.eth_sender`, set in `on_reply`), so a third party can submit a claim but cannot redirect it (test `claim_by_third_party_credits_the_proven_sender`). Spending that credit on LEZ then needs proof of control of the Ethereum sender key (not implemented in the reference). If you want a LEZ recipient, it must be cryptographically bound on the Ethereum side (for example an event field or commitment the depositor wrote, checked by your predicates), never taken from the claim message.

## Migrating when the weak-subjectivity period elapses (F10)

An instance is never refreshed in place; there is no instruction to change its checkpoint (F13).
1. Compute the new `instance_id = attest_program::instance_id(cfg, trusted_block_root)` for the new checkpoint (the only id `Init` accepts). Anyone can `Init` it from a recent bootstrap (the call rejects a stale checkpoint with 1105). Verify the new checkpoint independently (TRUST-ASSUMPTIONS.md section 3) and confirm operators will run it.
2. Because `VaultConfig.instance_id` is fixed at `InitVault`, create a new vault pinned to the new instance (a new `vault_id`) rather than editing the old one. Nothing in the program can re-point a vault.
3. Public nullifiers are keyed on `vault_id ‖ statement_id` (rule 1), so the new vault starts with an empty nullifier set: a deposit already credited by the old vault can be credited again by the new one. Before you open the new vault, decide the cut-over: either have the new vault accept only deposits made to a new Ethereum vault address, or carry the old vault's credited statement ids over (check them before crediting). Private nullifiers `pnf(nk)` are per consumer program, so they carry over as long as you keep the same consumer program.
4. Facts already attested under the old instance keep their value (R3). Only new attestations need the new instance. Migrate before 1105 starts appearing.
5. `ws_period_epochs` is short on Sepolia (279 epochs, about 29.8 h; mainnet 3,537 epochs, about 15.7 days; D-LC-6): monitor the instance's finalized slot and migrate early. Untested end to end.

Replacing a consumer program (new `ATTEST_PROGRAM`, new code) follows the same pattern: deploy new, move users, retire old.
