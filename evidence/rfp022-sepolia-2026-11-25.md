# RFP-022 Sepolia end-to-end run on risc0 3.1.0 (2026-11-25)

Applies to guest ImageIDs bridge `fda709a30ef31641020ed73d49ab6a66093a20936d6c6b538fa9063691b4149e` (LEZ program) and burn_member `0x905d2b8ca788d62120ce230e219446f772188d7f3e1023f649a391236a1aa449` (`MEMBERSHIP_IMAGE_ID`), both Docker-built; risc0-zkvm 3.1.0; LEZ `6aaabe5` (v0.4.0-rc3 plus the risc0 3.1.0 bump). The LEZ standalone sequencer binary carries the upstream fix `f55d961` (see "Changes"). This run supersedes the 2026-11-10 run in [rfp022-sepolia.md](rfp022-sepolia.md); the design, trust model and the steps of the flow are the same.

## Why this run exists

RISC Zero advisories GHSA-g6qg-9j8p-7j87 and GHSA-mm6c-35cm-g4x2 affect risc0-zkvm below 3.1.0 and the risc0-ethereum Groth16 verifier below 3.1.0. The 2026-11-10 vault pinned `RiscZeroGroth16Verifier` v3.0.0 (`0x2a09…a84D`, selector `0x73c457ba`), which RISC Zero has emergency-stopped. The code now pins risc0-zkvm 3.1.0 and the v3.1.0 verifier `0x8c915b5071206C6E328BC18529586c513408aB3b` (selector `0xe71e6620`). Receipts and ImageIDs from 3.0.5 do not carry over, so the guests were rebuilt, the vault was redeployed and the flow was run again.

## Scope and trust notes

- Same as the 2026-11-10 run: the root path is interim and custodial (2-of-2 `EcdsaRootVerifier`, release delay `D = 600 s`, demo caps, root revocation); every LEZ transaction used `RISC0_DEV_MODE=1`.
- Different from the 2026-11-10 run: **both root signers and the Groth16 prover ran on one machine** (an Apple M2 Max, macOS), because the separate prover host was not available. `B22_SIGNER2_HOST=local` and `--groth16-host local`. Signer 2's key was made by `b22 gen-signer` on that machine and exists only there. This run shows the code path, not separation of signer custody. The transcript header was printed before `b22` learned to say so (it reads "signer 2 on signer host 2 (sign-root over ssh)"); `b22` now prints "BOTH ON THIS MACHINE" when `B22_SIGNER2_HOST=local`.
- The two Ethereum `release` transactions carry real proofs: succinct `burn_member` receipts wrapped to Groth16 locally (Docker image `risczero/risc0-groth16-prover:v2026-10-20.1` under amd64 emulation) and verified on chain by the v3.1.0 verifier.

## Changes needed for risc0 3.1.0 and LEZ 6aaabe5

- Pins: risc0-zkvm 3.1.0, risc0-build 3.0.7, risc0-binfmt 3.0.6, rzup `cargo-risczero`/`r0vm` 3.1.0, LEZ `6aaabe5` in every crate and both module workspaces, `lib/risc0-ethereum` at v3.1.0.
- LEZ moved `fee` out of `execution` and placed it after `nonces` in `TransactionMessage`. `lez-client` writes the public-transaction borsh layout by hand, so its field order was fixed; `public_tx_matches_lee` caught it.
- LEZ's `execute_and_prove` publication callback now takes the whole batch, including an empty one; the test harness returns an empty list for an empty batch.
- `V03State::with_named_programs` is gone; tests build genesis with `GenesisBuilder::with_programs_at`.
- A fresh LEZ standalone sequencer at `6aaabe5` exits with `ChannelWithoutBlocks`: the standalone mock reports a channel tip slot before any block is stored. Upstream fixed this in `f55d961` (2026-11-23, 13 lines, standalone mock only). The README and `e2e.yml` apply that patch to the vendored sequencer; the crates still pin `6aaabe5`.
- `remote_groth16` now creates `$HOME/r0work` before running `bridge-prover` (see attempts), and `--groth16-host local` / `B22_SIGNER2_HOST=local` run the wrap and signer 2 on the current machine.

## Not covered by this run

- LEZ proofs: still dev mode, as before. The real LEZ `Burn` proof in [rfp022-sepolia.md](rfp022-sepolia.md) Section 5 was measured on risc0 3.0.5 and was not repeated.
- Benchmarks in `docs/BENCHMARKS.md` are risc0 3.0.5 figures and were not re-measured. LEZ `6aaabe5` also changed how private transactions are charged (the fixed `PROOF_BYTES` storage term is gone), so the private-transaction gas figures recorded at `1806e87` may differ on `6aaabe5`.
- `cross_operation_unlinkable` (`crates/program-tests/tests/bridge.rs`) passes in dev mode, as CI runs it. Run once without `RISC0_DEV_MODE` (real proofs, about 3 hours on this machine), it failed: one holder's claim shared 1,127 32-byte windows with the same holder's later transfer and burn that do not occur in the other holder's transactions. The test had not been run with real proofs before, so it is not known whether this predates the upgrade. Open.
